# リスク基準

人は普段は何も承認しません。このファイルの「高リスク」に当てはまる変更と、「人が入る条件」に当てはまったときだけ、escalate スキルで人に判断を仰ぎます。triage・plan・merge-gate の各スキルは、同じこの基準で判定します。

このファイル自体の変更は高リスクです。

## 1. リスクの判定

| 判定 | 例 | マージ | 本番反映 |
| --- | --- | --- | --- |
| `risk:low` | 文言・見た目の小さな修正、テスト追加、文書、依存のパッチ／マイナー更新 | 自動 | 自動（段階公開） |
| `risk:medium` | 新しい画面や API の追加、既存機能の変更、複数ファイルにまたがる修正 | 自動 | 自動（段階公開、新機能はフィーチャーフラグの後ろ） |
| `risk:high` | 下の「高リスクの変更」に1つでも当てはまるもの | **人が承認** | 承認後に自動 |

迷ったら高い方に判定します。plan や実装の途中で判定が上がったら、ラベルを付け替えて Issue にコメントします。判定を下げるのは、理由を PR に書いたときだけです。

## 2. 高リスクの変更

次のどれかに当てはまる変更は `risk:high` です。

1. DB のスキーマ変更（マイグレーション）
2. 認証・認可・権限・セッションの扱い
3. 課金・決済・料金計算
4. 個人情報・機微データの扱い、それらのログ出力
5. インフラ・ホスティング・ドメイン・DNS の設定
6. 外部への自動送信（メール・LINE・決済・SNS 投稿など、利用者や第三者に届くもの）
7. データの一括削除や、元に戻せないデータ変換
8. 新しい有料サービス・外部 API の導入、依存のメジャー更新
9. セキュリティ設定（CORS・CSP・暗号化）と秘密情報の扱い
10. CI/CD・自動化・安全装置の設定（`.github/workflows/`、`.claude/settings.json`、`CODEOWNERS`、このファイル）
11. 利用規約・プライバシーポリシー・料金表示の文言

1・2・3・5・10 に当たるファイルは `CODEOWNERS` にも登録し、GitHub の設定でも人の承認がないとマージできないようにします。AI の判定ミスだけに頼らないためです。

## 3. 人が入る条件

| 条件 | 理由 | 人がやること |
| --- | --- | --- |
| 高リスクの変更 | 戻せない、または被害が大きい | PR を確かめてマージを承認 |
| 仕様の大きな解釈違いがありうる（新機能、料金や規約に関わるもの） | 作り直しのコストが大きい | spec の仮定を確かめて OK か修正を返す |
| 新しい見た目の方向性（新しい種類の画面、`docs/design/` の基本ルール・配色の変更、アプリの最初の見た目） | 見た目と使いやすさはオーナーの好みと使う人で決まり、いちばん大事にしているため | design スキルの見本から選ぶ（「A と C を混ぜて」のような返事でよい） |
| Claude と Codex の意見が2往復しても割れる | AI 同士では決着しない | 両者の主張を読んで選ぶ |
| 自己修正が3回失敗した | 無限ループと利用量の浪費を防ぐ | 方針を示すか Issue を閉じる |
| 自動ロールバックが起きた、またはロールバックで直らない | 利用者への影響が出ている | 報告を確かめ、必要なら介入 |
| 両方の AI が利用上限で止まった | 自走できない | 何もしなくてよい（回復後に自動再開）。急ぐときだけ指示 |

## 4. 自動マージの条件

merge-gate スキルは、次の **すべて** を満たすときだけ自動マージします。

1. CI がすべて緑
2. 作った側と別の AI のレビューで、未解決の指摘がない
3. verify で受け入れ条件を満たしたことを確認済みで、ui-review で必須の指摘がない（画面・操作の変更がある場合）
4. リスク判定が `risk:low` か `risk:medium`
5. PR に仮定・確認結果・残課題が書かれている

1つでも満たさないときはマージしません。4 だけを満たさないときは escalate します。
