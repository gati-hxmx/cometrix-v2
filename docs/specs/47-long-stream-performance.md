# #47 長い配信（10時間・10万コメント）でも速く取得・表示できる

## 目的

長い配信を分析する人が、待たされず、途中で失敗しても最初からやり直さずに済むようにする。ロードマップ段階 A（土台）。画面の見た目は変えない（既存の分析画面の速さだけを確かめる・直す）ので、新しい画面・design は不要。

## 前提（順序）

[#43](https://github.com/gati-hxmx/cometrix-v2/issues/43)（PR #44）が `src/worker/fetch-chat.ts`・`twitch-chat.ts`・`process.ts` と `jobs.result` の使い方を変えている。このタスクの実装は **#44 のマージ後に main から始める**（先に始めると衝突する）。それまでは仕様と計画までを進める。

## 目安（目標値）

測る環境：ローカルの Postgres（compose の標準）、10万コメント・10時間の仮データ（`scripts/bench` が作る。同じ数・同じ乱数の種で毎回同じデータ）。

| 項目 | 目安 |
| --- | --- |
| 10万コメントの保存と集計（取得を除く、ワーカーの保存〜done まで） | 10 秒以内 |
| 分析画面の最初の表示（グラフの30秒ごとの集計 API） | 300ms 以内（サーバー側） |
| チャット一覧の取り直し（`messages` API・絞り込みなし／あり） | 200ms 以内／500ms 以内（サーバー側） |
| グラフの拡大・チャット一覧のスクロール | 描画 1 フレーム 50ms 以内（操作が引っかからない） |

目安を超えたものは、原因を直すか、PR に理由と「別 Issue にする」を書く。

## 受け入れ条件

### 計測
- `scripts/bench` を実行すると、仮データを入れて上の表の各項目を測り、表で出力する。結果を PR に貼る。
- 仮データは `bench` 専用のジョブとして作り、終わったら消す（普段のデータに触らない）。

### 取得の再開
- Twitch：取得の途中（ページの途中）で失敗しても、再試行のとき、保存済みの最後のカーソルから続きを取り、最初から取り直さない。結果のコメントは、途切れず取った場合と同じ（重複なし・欠けなし）。
- YouTube（yt-dlp）：再試行のとき、同じ作業フォルダを使い、yt-dlp が途中のファイルから続きを取る。作業フォルダは終わったとき（done・failed）に消す。続きの取得ができない（ファイルがない）ときは、最初から取る。
- 再試行は今までどおり最大 `MAX_ATTEMPTS` 回。上限に達したら failed で、保存途中のコメントは消す。
- 途中の失敗を作るテストで、続きから取れたこと（取り直したページ数・結果の件数）を確かめる。
- 完了したジョブのコメントは、1度の取得で取ったものと同じ件数・順で保存される（再開してもコメントが二重にならない）。

### 保存
- 10万コメントの保存は、1回の大きなトランザクションにせず、一定件数ずつ書き、取り直しても二重にならない（再開の単位と揃える）。
- 保存中は `jobs.updated_at` を進め、長い保存でも「止まった」と回収されない。

### 表示
- 10万コメントのジョブで、分析画面を開いてからグラフが出るまでの API が目安内。
- グラフの拡大・チャット一覧の追従・絞り込みで、API が目安内で、画面が引っかからない（ブラウザで 375・1024・1440px を確かめ、結果を PR に書く）。
- 目安を超える API は、索引・クエリ・件数の上限を直す。DB の索引・表の変更が要るときは、マイグレーションを同じ PR に含め、risk:medium として扱う。

## 範囲外

- 取得そのものを速くする（YouTube・Twitch 側の速度は変えられない）。
- 10時間を超える配信・100万コメント級。
- 古い分析の掃除（#50）、同時取得の上限（#49）、通しテストと画面写真（#48）。
- yt-dlp のタイムアウト（#46）。ただし再開が #46 の修正と同じ箇所に触れるときは、先に #46 を入れる。

## 仮定

- 「目安の時間」は Issue に数値がないため、上の表を妥当な値として置いた。測った結果で、実現できない値は PR で理由つきで直す。
- YouTube の再開は、yt-dlp 自身の続き取得（`--continue`、既定で有効）に任せ、自前のカーソルは持たない。チャットのリプレイは yt-dlp が断片ごとに取るため。再開できなかったときは最初から取る（失敗にはしない）。
- Twitch の再開位置は DB に持つ（カーソル）。置き場は #44 の `jobs.result` の進み具合と合わせ、新しい列が要るかは plan で決める。
- ワーカーが落ちて作業フォルダが消えたときは、YouTube は最初から取り直す（コンテナの外に置く保証はしない）。
- 画面の操作の速さは、ブラウザでの手動確認（verify）と API の計測で見る。自動の画面テスト（Playwright）は #48 の範囲。
