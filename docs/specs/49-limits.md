# 49 入れた URL の確認と、取得の上限

## 目的

公開したときに、悪用やサーバーの詰まりを防ぐ。使う人には、混んでいるときに「少し待ってから」と分かる形で伝える。

## 今の状態

- URL の確認は `parseVideoUrl`（`src/lib/youtube-url.ts`）が済ませている。YouTube・Twitch のアーカイブ以外は `invalid_url` で、取得は始まらない。取得に使うのは検証後に作り直した URL だけで、入力の URL はそのまま使わない。
- ワーカーは1つにつき1件ずつ処理する。ジョブの数と連打には上限がない。

## 受け入れ条件

1. 許していない URL（内部アドレス `http://127.0.0.1/…`、`http://169.254.169.254/…`、別サイト、`youtube.com.evil.example`、userinfo 付き `https://youtube.com@evil.example/…`、`file:`）を POST すると、ジョブを作らずに 400 `invalid_url` を返す（テストあり）。
2. 未完了（queued か running）のジョブが `MAX_PENDING_JOBS`（初期 50）以上のとき、新しい動画の依頼は 503 `busy`（`Retry-After` つき）で断り、ジョブを作らない。すでにある動画の依頼（既存ジョブを返す場合）は断らない。49 件なら受け付ける（境界）。
3. 同じ接続元が `RATE_LIMIT_MAX`（初期 10）回／`RATE_LIMIT_WINDOW_SEC`（初期 60 秒）を超えて POST すると 429 `rate_limited`（`Retry-After` つき）を返す。10 回目までは通り、11 回目で断る。時間が過ぎれば再び通る。接続元ごとに数える。不正な URL の依頼も回数に入る。
4. running のジョブが `MAX_CONCURRENT_FETCH`（初期 2）以上のとき、ワーカーは新しいジョブを拾わず、queued のまま待たせる。running が減れば拾える（テストあり）。
5. 429・503 のとき、画面はお知らせ（基本 8-1）に「混んでいます。少し待ってからもう一度お試しください。」を出し、入力した URL は残す。ボタンは押せる状態に戻る。

## 範囲外

- ログインした利用者ごとの上限、プランごとの違い（認証がまだない）。
- 複数サーバーで共有する連打の制限（今は1プロセス内の数え方）。
- 取得の打ち切り時間（#46）。

## 仮定

- 接続元は `x-forwarded-for` の先頭、なければ `x-real-ip`、どちらもなければ共通の1つとして数える。逆プロキシの背後に置く前提で、直接公開すると詐称できる。公開時に Caddy などで上書きする（`docs/setup.md` に書く）。
- 連打の数え方はメモリ内の固定窓。再起動で消えてよい。DB のスキーマは変えないため、リスクは medium のまま。
- 上限の値は環境変数で変えられる。初期値は小さな VPS 1台を想定した妥当な値。
- 待ち行列の上限は「断る」を選ぶ（際限なく積まない）。
