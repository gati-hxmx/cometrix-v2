# #3 YouTube アーカイブのチャットを取得して30秒ごとに集計する

## 目的

分析画面（#4）とチャット一覧（#5）の元データを作る。YouTube Live のアーカイブ URL を登録すると、ワーカーがチャットを取得し、30秒ごとのコメント数と各コメントを DB に保存する。画面はこの Issue の範囲外。

## 受け入れ条件

### ジョブ
- URL を登録すると `jobs` に `queued` の行ができ、ジョブ ID が返る（`POST /api/jobs`）。
- ワーカーは `queued` を古い順に1件ずつ拾って `running` にし、終わったら `done`、失敗なら `failed`（理由つき）にする。複数のワーカーが同時に動いても、同じジョブを二重に拾わない。
- 同じ動画の URL が `queued`／`running`／`done` のジョブとして既にあるとき、新しいジョブは作らず既存のジョブ ID を返す。`failed` のときは新しく作る。
- `running` のまま10分以上更新がないジョブは、ワーカー起動時と定期確認で `queued` に戻す（`attempts` が3に達していたら `failed`）。

### URL
- `youtube.com/watch?v=`・`youtu.be/`・`youtube.com/live/` の形から動画 ID（11文字）を取り出し、正規化した URL で保存する。
- YouTube の URL でない・動画 ID が取れない入力は、ジョブを作らず 400 と理由（`invalid_url`）を返す。Twitch の URL は今回は未対応（`unsupported_url`）で 400（#6 で対応）。

### 取得と集計
- チャットは yt-dlp（ライブチャットのリプレイ）で取得する。取得部分は差し替えられる形にし、テストはネットワークを使わず保存済みのサンプルで行う。
- 各コメントを `chat_messages`（ジョブ ID・動画内の時刻ミリ秒・ユーザー名・本文）に保存する。同じジョブを再処理しても重複しない（ジョブ単位で入れ替える）。
- `chat_buckets`（ジョブ ID・区間開始秒・コメント数）に、0秒から30秒ごとの集計を保存する。区間は [開始, 開始+30秒)。0件の区間も、0秒から最後のコメントを含む区間まで連続して保存する。
- 動画開始前（時刻が負）のコメントは、集計にも一覧にも含めない。
- スーパーチャット等で本文が空のコメントは、本文を空文字で保存し、件数に数える。
- 完了時、`jobs.result` に動画 ID・タイトル・コメント総数・最終区間を入れる。

### 失敗の理由（`jobs.error` にコードと日本語メッセージ）
- `invalid_url`：URL が不正
- `no_chat`：チャットがない動画（チャットリプレイが無効・コメント0件）
- `video_unavailable`：非公開・削除・メンバー限定
- `fetch_blocked`：YouTube に IP やボットとして止められた
- `fetch_failed`：その他の取得失敗（外部コマンドの異常終了・タイムアウト）
- 原因の違うものを1つの理由にまとめない。

### 環境確認
- VPS 上で実際にチャットが取れるかを確かめ、結果を Issue に書く（手順は文書に残す）。VPS に入れない場合は、取れる前提にせず「未確認」と書く。

## 範囲外

画面（#4・#5）、Twitch（#6）、ログイン・利用制限（#7 以降）、ライブ中の配信、結果の自動削除。

## 仮定

1. 取得は旧版の Python ではなく、スタック決定（#1）どおり TypeScript から yt-dlp を外部コマンドで呼ぶ。yt-dlp はワーカーの Docker イメージに入れる。
2. 登録は認証なしの `POST /api/jobs`。ログインは #7 で入れるので、今回は手元利用前提（公開は #12）。
3. 状態確認用に `GET /api/jobs/:id`（状態・理由・result）を足す。
4. 区間の定義は上記のとおり固定する。旧版と1区間ずれる可能性がある。
5. DB は `chat_messages`・`chat_buckets` を追加するマイグレーションを作る（リスク high：人の承認でマージ）。
6. yt-dlp は無料の OSS で、新しい外部ツールの導入にあたる（リスク基準 8）。承認時に確認してもらう。
