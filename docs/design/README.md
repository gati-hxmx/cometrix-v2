# デザインと UI のルール

このテンプレートでいちばん大事にするのは、画面の使いやすさと見た目です。AI が自走で画面を作っても品質がぶれないように、ここに決まりをまとめます。新しい画面や変更は、まずこのルールに合わせます。ユーザーの指示がルールと合わないときは指示を優先し、この文書も同じ PR で書き直します。

土台は Hana（給与・シフト管理）の開発で、オーナーの指示と選択を積み重ねてできたルールです。Hana 固有の画面や業務の話を外し、どのアプリにも使える形にしています。

## ルールの地図

ルールは3つの層に分かれています。上の層ほど優先します。

| 層 | 文書 | 中身 |
| --- | --- | --- |
| ① 前提 | この文書の「使う人」「見た目を選ぶときの考え方」と、[基本 9](layout.md#9-変えてはいけない決まり) | だれが使うか、デザインの考え方、変えてはいけない決まり |
| ② 共通の基本ルール | [画面づくりの基本](layout.md) | 画面の配置・パネル・押しやすさ・お知らせ・確認のしかた・数え方・サイトの地図 |
| | [部品づくり](components.md) | 見て操作する、文字を打たせない、アイコン中心、操作の分け方、共通部品 |
| | [配色](colors.md) | 白い地と細い枠、色の使い分け、色の変数 |
| | [アイコン](icons.md) | 描き方と置き方、1つの絵に1つの意味 |
| ③ 画面ごとの仕様 | `docs/screens/<画面>.md` | 各画面の「使う人と最初の画面」、配置、状態（アプリごとに作る） |

調べるときだけ読むもの：[ルールの経緯](history.md)（なぜそう決めたか）。

書き方の決まり：

- 章には番号を付け、ほかの文書からは「基本 7」「部品 4-2」のように指します。
- やさしい「です・ます」で書きます。同じ決まりは1か所だけに書き、ほかの場所からは参照します。
- 比べた案の名前やくわしい経緯は [ルールの経緯](history.md) に書き、各章には「経緯：日付（[経緯](history.md)）」の1行だけを置きます。
- 画面ごとの仕様は、最初に「使う人と最初の画面」の表を置きます（下の「使う人」と [基本 1](layout.md#1-pc-とスマホは別々に最適化する)）。

## 使う人

アプリを始めるとき（stack-select・最初の spec）に、この表を埋めます。どの画面も、だれが・どこで・何をしに開くかを、画面の仕様の最初に1行で書きます。

| 使う人 | どこで | 何をしに | 気をつけること |
| --- | --- | --- | --- |
| 配信のアーカイブを見返す人 | PC が中心、ときどきスマホ | URL を入れて、コメントが盛り上がった時刻を見つけ、そこから再生する | グラフと動画とチャット一覧を行き来するので、1つの画面で用が済むこと。最初の画面（#2）でオーナーが選んだ形：[トップ](../screens/top.md)・[分析画面](../screens/analysis.md) |

- 対応する言語が複数あるときは、どの言語でも同じように使えることを確かめます。長くなる言語を前提に、切り替えの札などには短い名前を最初から用意します（[部品 3-6](components.md#3-文字の表示はアイコン中心にして場所を取らない)）。

## 見た目を選ぶときの考え方

新しい見た目を作るとき・案を出すときは、まずこの6つに合わせます。くわしい決まりは（ ）の章にあります。

1. **すでにある、気に入られている画面にそろえる**：新しい形を作る前に、アプリの中でオーナーが選んだ画面の形（角丸の四角、大きな数字など）から始めます。最初の画面は design スキルで選んでもらいます。
2. **強い色を使わず、白い地で控えめに**：赤など強い色の面は使わず、薄い色と細い枠にします。目立たせるのは、見てほしい所だけです。**赤と ⚠ は今日やらないと困るものだけ**で、あとでよいものは灰色にします（[配色 2-1](colors.md#2-1-赤と--は今日やらないと困るものだけ)）。
3. **文字を減らして、印で伝える。ただし覚えないと読めない印にはしない**：言葉の代わりに記号（✕・⚠・✓）やアイコンを使います。**数には単位を付けます**（「9人」「19時」「あと1」「⚠2枚」。数だけの「9」「19」にしない）。凡例を読まないとわからない印は作らず、単位や短い言葉（「まだ」「なし」「✓済」）で印そのものを読めるようにします。押すボタンのアイコンには、スマホでは短い言葉を必ず添えます（[部品 3-1](components.md#3-文字の表示はアイコン中心にして場所を取らない)・[基本 4](layout.md#4-切り替えボタンの位置)）。
4. **画面を移らずに、その場で済ませる**：スマホで表やカレンダーの項目を押したら下からシートを出し、シートの中で前後へ移ったり、追加したりできるようにします（[基本 6-2](layout.md#6-2-パネルの決まり)）。
5. **スマホは指で押しやすく、PC は一度にたくさん見せる**：スマホは大きな数字と、アイコンを上にした大きな四角の札。PC は同じ四角の中に中身を並べ、押さなくても見えるようにします（[基本 1](layout.md#1-pc-とスマホは別々に最適化する)）。
6. **いいところを組み合わせて絞る**：見た目を決めるときは、スマホと PC それぞれ4案ほどの見本を出し、選ばれた案や2つの案を混ぜた形で次の案を作って、少しずつ詰めます。1回で決めきろうとしません（design スキル）。

## オーナーがよく指摘すること

Hana でオーナーに何度も直してもらった所を18にまとめたものです（Hana の基本 0-2、2026-11-13 に12、2026-11-15 に13〜18）。**新しい画面・案・PR は、オーナーに見せる前・PR を出す前に、この18個を1つずつ自分で確かめます**。指摘されてから直すのではなく、最初から守ります。くわしい決まりは（ ）の章にあります。例はすべて Hana での指摘です。

1. **使う人（IT が苦手な人も）が迷わないか**：画面の文は専門の言葉にせず、使う人の言い方で書きます。一度押しただけで大きく変わる所は、押しまちがえても何も起きない形にします（[基本 2](layout.md#2-ヘッダー画面の一番上)）。例：「確定解除」「スナップショット」、国旗1回でアプリ全体の言語が変わっていた。
2. **上のメニューと本体のあいだに何も置かない**：注意・説明・お知らせは、関係するマス・行・札の中か近くに置きます（[基本 2-1](layout.md#2-1-上のメニューと本体のあいだには何も置かない)）。例：黄色の「記入漏れ」の箱。
3. **要らないものは出さない（引き算）**：新しい表示・札・列・ボタンを足す前に、「なくても困らないか」「ほかの場所と同じことを言っていないか」を考えます。迷ったら出しません。直すときも、まず減らせる物がないかを先に見ます。例：「工程バーっているかな？」、ホームの札が「多すぎる」、「サイトの地図って文字いらんな」、同じ工程を2度出していて「いらんくね」。
4. **同じことは1か所だけ**：同じ数・同じ設定・同じ入口を2か所に作りません（[基本 5](layout.md#5-同じ情報は1か所にまとめる)・[基本 12](layout.md#12-数え方どの画面でも同じ数にする)）。例：やることが6か所にあって数がばらばら。
5. **パネルは本当に要るときだけ**：その場で直せるか、[小さなメニュー](components.md#5-9-小さなメニュー)で済まないかを先に考えます（[基本 6-1](layout.md#6-1-パネルにするかの判断)）。例：「選ぶのにサイドパネル要る？プルダウンで良くない？」。
6. **同じ種類のページは同じ形にそろえる**：新しいページは、作る前に同じ種類の今あるページ（上の枠・戻る札・グラフ・一覧）と並べて比べ、[共通の部品](components.md#5-共通部品を使い回す)で作ります。そのページだけの形にしません。例：あるページの上のメニューだけ他と違っていた、戻るボタンを右に置いた（左の「‹ 一覧」の札にそろえる）。
7. **強い色を使わず、赤と ⚠ は本当に急ぐものに絞る**：面は白と薄い色。赤と ⚠ は[配色 2-1](colors.md#2-1-赤と--は今日やらないと困るものだけ)の決まりに従い、ここでは足しません。例：赤は「強すぎる」、ほぼ全部のマスに ⚠ が付いていた。
8. **印は覚えなくても読める**：数には単位を付け、凡例を読まないとわからない印は作りません。スマホのアイコンのボタンには短い言葉を添えます（[考え方 3](#見た目を選ぶときの考え方)・[部品 3-1](components.md#3-文字の表示はアイコン中心にして場所を取らない)）。例：「19」→「19時」、「9」→「9人」。
9. **マス・札・行の中に収まる**：長い名前・大きな数・長くなる言語でも、文字が切れない・重ならない・はみ出さないことを、見せる前に確かめます。入らないときは文字を小さくせず、短い名前・2行・「…」（押すと全部見える）にします。仮のデータは短いので、長い名前（長い配信タイトル・長いユーザー名）を入れて確かめます。
10. **使う人のやり方に合わせ、仕事は本来のページで**：その人がしない作業は出さず、作業はそれが本来あるページに出します。
11. **実際の使い方のリズムに合わせる**：やること・⚠・催促は、使う人の本当の流れに合わせて出します。まだやれないことを毎回催促しません。
12. **打たせない・まちがえても戻せる・押しやすい・数が増えても困らない**：選ぶだけで入れられること（[部品 2](components.md#2-文字を打たせない)）、確認より［元に戻す］（[部品 4-2](components.md#4-操作のしかた)）、［元に戻す］のお知らせは ✕ まで残す（[基本 8-1](layout.md#8-1-お知らせ画面の下)）、押す所は44px以上（[基本 8](layout.md#8-押しやすさ読みやすさお知らせ)）、対象の数に頼る形（タブを数だけ並べる）にしない。
13. **開いたものは上に重ねる。下を押し出さない**：小さなメニュー・⋮・▾・ⓘ は、下の行の上に浮かべて重ね、押しても下の要素を動かしません（[部品 5-9](components.md#5-9-小さなメニュー)）。行の下に中身を開く › も、開くのは押した1つだけです。例：「押した時に下の要素がぐっと下に押し出されるのが気になる」。
14. **細かく変えるたびに保存しない**：何回か押して決める値（時刻・範囲など）は、変えても保存せず、変えると出る［この〇〇で保存］［キャンセル］で1回だけ保存します。1回押せば決まる選択は、すぐ保存＋［元に戻す］のままです（[部品 4-2](components.md#4-操作のしかた)）。例：「変更するたびに保存されてうざい」。
15. **上の枠は1行、あまり使わない操作は ⋮ に**：上の枠は「対象 ▾｜‹ 期間 ›｜⋮」のように1行にし、あまり使わない操作はアイコンだけの ⋮ から重なるメニューで出します（[基本 4](layout.md#4-切り替えボタンの位置)、[部品 3-1](components.md#3-文字の表示はアイコン中心にして場所を取らない)）。メニューと同じ所へ戻るだけの戻る札は置きません。例：「上部メニューが多すぎる」「その他って文字はいらない」。
16. **PC は左に一覧・右に中身、右でそのまま直す**：同じ種類のものが並ぶページは、PC は左に一覧・右に選んだ1件の中身、スマホは一覧 → 中身です（[基本 7](layout.md#7-詳細画面の配置)）。右の中身はそこで直接見て直せる形にし、「開く → また項目を選ぶ → サイドパネル」と重ねません。例：「開いてからまた項目を出してサイドパネルが開いてと煩わしい」。
17. **スマホで読みにくい表は1件ずつ**：人（対象）×項目の広い表は、スマホでは横に流さず、「‹ 名前 ▾ ›」で1件ずつ切り替えて見せます（[部品 5-10](components.md#5-10-1件ずつ切り替えと写真動画を前に大きく)）。
18. **ゆったり1列・写真は切らない・ボタンは字の幅**：1列で足りるものは2列にせず、まわりに余白を取ります。写真は切らずに全部見せ、中身が読める大きさにします。ボタンは横いっぱいにせず字の幅です（スマホの下に固定する保存などは除く）。写真・動画は押すと前に大きく出し、まわりを押すと戻ります。例：「１列でいいよ」「写真が見切れてる」「ボタンデカすぎ」「ギチギチだからもう少し余白を意識して」。

あわせて守ること：

- 見た目を決めるときは4案を出し、選ばれた案や混ぜた形で次の4案を作って詰めます（design スキル）。前の案も残しておきます。
- 見せる前に「これ基本ルールに則ってる？」と自分で聞き、各項目を1つずつ見直します。PR の本文には、各項目のうち今回の画面に関係する番号と、確かめた結果を書きます（ship）。
- 新しいやり方を足しても、オーナーが言うまで今のやり方は消しません。
- 新しく指摘されたことがどの項目にも入らず、ほかの画面でも起きそうなら、ここに足します。

経緯：2026-11-22 Hana の基本 0-2 を取り込んだ（[経緯](history.md#オーナーがよく指摘すること)）。

## AI が守ること

- 画面を作る・変えるときは、このフォルダの該当する章を読んでから作ります（implement）。作る前と PR を出す前に、[オーナーがよく指摘すること](#オーナーがよく指摘すること) の各項目を1つずつ確かめます。
- 新しい見た目の方向性を決めるとき（新しい種類の画面、デザインの基本ルールの変更）は、design スキルで見本を出してオーナーに選んでもらいます（[リスク基準](../risk-policy.md) の「人が入る条件」）。既存のルールと部品の組み合わせで作れる画面は、そのまま自走で進めます。
- 画面の変更は、[基本 10 の確認のしかた](layout.md#10-確認のしかた) をすべて確かめ、ui-review スキルで別の AI がレビューします。
- ユーザーがデザインについて指示・選択をしたら、該当する章を直し、[ルールの経緯](history.md) に1行足します（retro も定期的に見直します）。
- 画面がそろってきたら、ときどき「IT が苦手な使う人」の目線で全体を点検します（赤や ⚠ が多すぎて急ぎがわからない、凡例を覚えないと読めない、スマホで名前がわからないアイコン、お知らせがすぐ消える、専門の言葉、など）。見つけたことはルールに戻してから画面を直します。
