# デザインと UI のルール

このテンプレートでいちばん大事にするのは、画面の使いやすさと見た目です。AI が自走で画面を作っても品質がぶれないように、ここに決まりをまとめます。新しい画面や変更は、まずこのルールに合わせます。ユーザーの指示がルールと合わないときは指示を優先し、この文書も同じ PR で書き直します。

土台は Hana（給与・シフト管理）の開発で、オーナーの指示と選択を積み重ねてできたルールです。Hana 固有の画面や業務の話を外し、どのアプリにも使える形にしています。

## ルールの地図

ルールは3つの層に分かれています。上の層ほど優先します。

| 層 | 文書 | 中身 |
| --- | --- | --- |
| ① 前提 | この文書の「使う人」「見た目を選ぶときの考え方」と、[基本 9](layout.md#9-変えてはいけない決まり) | だれが使うか、デザインの考え方、変えてはいけない決まり |
| ② 共通の基本ルール | [画面づくりの基本](layout.md) | 画面の配置・パネル・押しやすさ・お知らせ・確認のしかた・数え方・サイトの地図 |
| | [部品づくり](components.md) | 見て操作する、文字を打たせない、アイコン中心、操作の分け方、共通部品 |
| | [配色](colors.md) | 白い地と細い枠、色の使い分け、色の変数 |
| | [アイコン](icons.md) | 描き方と置き方、1つの絵に1つの意味 |
| ③ 画面ごとの仕様 | `docs/screens/<画面>.md` | 各画面の「使う人と最初の画面」、配置、状態（アプリごとに作る） |

調べるときだけ読むもの：[ルールの経緯](history.md)（なぜそう決めたか）。

書き方の決まり：

- 章には番号を付け、ほかの文書からは「基本 7」「部品 4-2」のように指します。
- やさしい「です・ます」で書きます。同じ決まりは1か所だけに書き、ほかの場所からは参照します。
- 比べた案の名前やくわしい経緯は [ルールの経緯](history.md) に書き、各章には「経緯：日付（[経緯](history.md)）」の1行だけを置きます。
- 画面ごとの仕様は、最初に「使う人と最初の画面」の表を置きます（下の「使う人」と [基本 1](layout.md#1-pc-とスマホは別々に最適化する)）。

## 使う人

アプリを始めるとき（stack-select・最初の spec）に、この表を埋めます。どの画面も、だれが・どこで・何をしに開くかを、画面の仕様の最初に1行で書きます。

| 使う人 | どこで | 何をしに | 気をつけること |
| --- | --- | --- | --- |
| 配信のアーカイブを見返す人 | PC が中心、ときどきスマホ | URL を入れて、コメントが盛り上がった時刻を見つけ、そこから再生する | グラフと動画とチャット一覧を行き来するので、1つの画面で用が済むこと。最初の画面（#2）でオーナーが選んだ形：[トップ](../screens/top.md)・[分析画面](../screens/analysis.md) |

- 対応する言語が複数あるときは、どの言語でも同じように使えることを確かめます。長くなる言語を前提に、切り替えの札などには短い名前を最初から用意します（[部品 3-6](components.md#3-文字の表示はアイコン中心にして場所を取らない)）。

## 見た目を選ぶときの考え方

新しい見た目を作るとき・案を出すときは、まずこの6つに合わせます。くわしい決まりは（ ）の章にあります。

1. **すでにある、気に入られている画面にそろえる**：新しい形を作る前に、アプリの中でオーナーが選んだ画面の形（角丸の四角、大きな数字など）から始めます。最初の画面は design スキルで選んでもらいます。
2. **強い色を使わず、白い地で控えめに**：赤など強い色の面は使わず、薄い色と細い枠にします。目立たせるのは、見てほしい所だけです。**赤と ⚠ は今日やらないと困るものだけ**で、あとでよいものは灰色にします（[配色 2-1](colors.md#2-1-赤と--は今日やらないと困るものだけ)）。
3. **文字を減らして、印で伝える。ただし覚えないと読めない印にはしない**：言葉の代わりに記号（✕・⚠・✓）やアイコンを使います。**数には単位を付けます**（「9人」「19時」「あと1」「⚠2枚」。数だけの「9」「19」にしない）。凡例を読まないとわからない印は作らず、単位や短い言葉（「まだ」「なし」「✓済」）で印そのものを読めるようにします。押すボタンのアイコンには、スマホでは短い言葉を必ず添えます（[部品 3-1](components.md#3-文字の表示はアイコン中心にして場所を取らない)・[基本 4](layout.md#4-切り替えボタンの位置)）。
4. **画面を移らずに、その場で済ませる**：スマホで表やカレンダーの項目を押したら下からシートを出し、シートの中で前後へ移ったり、追加したりできるようにします（[基本 6-2](layout.md#6-2-パネルの決まり)）。
5. **スマホは指で押しやすく、PC は一度にたくさん見せる**：スマホは大きな数字と、アイコンを上にした大きな四角の札。PC は同じ四角の中に中身を並べ、押さなくても見えるようにします（[基本 1](layout.md#1-pc-とスマホは別々に最適化する)）。
6. **いいところを組み合わせて絞る**：見た目を決めるときは、スマホと PC それぞれ4案ほどの見本を出し、選ばれた案や2つの案を混ぜた形で次の案を作って、少しずつ詰めます。1回で決めきろうとしません（design スキル）。

## AI が守ること

- 画面を作る・変えるときは、このフォルダの該当する章を読んでから作ります（implement）。
- 新しい見た目の方向性を決めるとき（新しい種類の画面、デザインの基本ルールの変更）は、design スキルで見本を出してオーナーに選んでもらいます（[リスク基準](../risk-policy.md) の「人が入る条件」）。既存のルールと部品の組み合わせで作れる画面は、そのまま自走で進めます。
- 画面の変更は、[基本 10 の確認のしかた](layout.md#10-確認のしかた) をすべて確かめ、ui-review スキルで別の AI がレビューします。
- ユーザーがデザインについて指示・選択をしたら、該当する章を直し、[ルールの経緯](history.md) に1行足します（retro も定期的に見直します）。
- 画面がそろってきたら、ときどき「IT が苦手な使う人」の目線で全体を点検します（赤や ⚠ が多すぎて急ぎがわからない、凡例を覚えないと読めない、スマホで名前がわからないアイコン、お知らせがすぐ消える、専門の言葉、など）。見つけたことはルールに戻してから画面を直します。
