# コードレビュー（review）

PR を作った側と別の AI が担当します。作った側が自分でレビューを代わることはしません（相手が利用上限のときは除き、その場合は PR にそう書く）。

## 観点（重要な順）

1. **正しさ**：受け入れ条件を満たすか。境界値・異常系・並行処理・タイムゾーン・丸め
2. **セキュリティ**：認可の抜け、入力の検証、秘密情報、個人情報のログ出力
3. **仕様からの逸脱**：範囲外の変更、仮定の妥当性
4. **テスト**：受け入れ条件に対応するテストがあるか。テストの削除・スキップ・期待値の書き換えで通していないか
5. **リスク判定**：[リスク基準](../../../docs/risk-policy.md) と合っているか。高リスクの変更が紛れていないか
6. **保守性**：既存の構成・共通部品に沿っているか（好みの問題は書かない）

## 出し方

- 指摘は該当行へのコメントで、1件ずつ「問題・理由・直し方の案」を書く。重大度（必須／推奨）を付ける。
- 必須の指摘がなければ、最後に「必須の指摘なし」とまとめる。
- これが2往復目で、まだ必須の指摘が残るときは、その旨を書く（address が escalate する）。

## 次に呼ぶスキル

- 必須の指摘あり → address（作った側）
- 必須の指摘なし・画面や操作の変更あり → ui-review（作った側と別の AI）
- 必須の指摘なし・画面の変更なし → merge-gate
