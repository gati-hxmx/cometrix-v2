# 仕様化（spec）

要望を、テストで確かめられる受け入れ条件に変えます。

## 手順

1. Issue・関連コード・既存の仕様文書を読み、今の振る舞いを把握する。
2. 次の形で仕様を書き、Issue にコメントする（大きいものは `docs/specs/<Issue番号>-<短い名前>.md` に置く）。
   - 目的（誰の何のためか）
   - 受け入れ条件：「〇〇のとき、〇〇になる」の形で、1つずつ確かめられるように書く。正常系・異常系・境界値を含める
   - 画面がある場合：画面ごとに「使う人と最初の画面」の表（だれが・どこで・何をしに開くか、375px でスクロールせずに見えるもの）。新しい画面は `docs/screens/<画面>.md` に置く（[デザインのルール](../../../docs/design/README.md)）
   - 範囲外：今回やらないこと
   - 仮定：あいまいだった点と、選んだ解釈・理由
3. あいまいな点は、もっとも妥当な解釈を選んで仮定に書き、先へ進む。次の場合だけ escalate する。
   - 仮定が外れると作り直しが大きい（新機能の中心的な振る舞い、料金・規約に関わるもの）
   - 高リスクの判断が仕様に含まれる
4. spec-check の指摘が返ってきたら反映し、反映したもの／しなかったものと理由を書く。

## 次に呼ぶスキル

- spec-check（Codex に仕様のチェックを頼む）
- ルールに形のない新しい見た目が要る → design（spec-check と並べて進めてよい）
- spec-check の指摘を反映済みなら plan
