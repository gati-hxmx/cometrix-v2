# 画面レビュー（ui-review）

このテンプレートでいちばん大事にするのは、画面の使いやすさと見た目です。コードのレビュー（review）とは別に、画面を実際に開いてルールに照らします。PR を作った側と別の AI が担当します。

## 読むもの

1. [デザインのルール](../../../docs/design/README.md) の「使う人」「見た目を選ぶときの考え方」
2. [画面づくりの基本](../../../docs/design/layout.md)・[部品づくり](../../../docs/design/components.md)・[配色](../../../docs/design/colors.md)・[アイコン](../../../docs/design/icons.md) のうち、変更に関係する章
3. 対象画面の `docs/screens/<画面>.md`（「使う人と最初の画面」の表）

過去のレビュー記録を、今回の確認の結果として使いません。

## 手順

1. PR の差分から、変わった画面・部品・操作の流れを決める。共通部品・共通の CSS が変わったときは、それを使う画面も対象にする。関係のない画面の作り直しには広げない。
2. PR のプレビュー環境（なければローカル）を、架空のデータで開く。本番のデータには触らない。
3. [基本 10 の確認のしかた](../../../docs/design/layout.md#10-確認のしかた) を1つずつ確かめる。少なくとも次は必ず見る。
   - 幅 375・1024・1440px のスクリーンショット（Playwright）。横のはみ出しと、表の中で認めた横スクロールを区別する
   - 375px の最初の画面に、仕様で決めたものがスクロールせずに見えるか
   - 対応する言語すべてと、文字を大きくしたとき
   - 空のとき・長い名前・エラー・権限がないときの状態
   - 指だけで同じことができるか、Tab・Enter・Esc、アイコンボタンの読み上げ名
4. 依頼に関係する一連の操作を実際に行う（例：追加 → 保存 → 元に戻す、パネルを開く → 入力の途中で閉じる → 確認が出る）。
5. ルールに書いていない見た目の判断が要る所は、[見た目を選ぶときの考え方](../../../docs/design/README.md#見た目を選ぶときの考え方) に照らす。新しい見た目の方向性が要るときは「デザインの判断が要る」と書く（design スキルへ）。

ブラウザが使えないときは、コード・CSS・テストの確認までを行い、「画面は未確認」と書く。必須の指摘がなくても、未確認のままでは merge-gate に「確認済み」と渡さない。

## 結果の出し方

PR に1つのコメントでまとめる。

- 重大な順に、1件ずつ：対象の画面と状態、再現の操作、ルール（「基本 2-1」のように章番号）、期待する見た目・動き、実際、直し方の案。重大度（必須／推奨）を付ける。
- 確かめた幅・言語・状態・操作の表と、スクリーンショット。
- 未確認の項目と理由。
- 最後に「画面レビュー：必須の指摘なし」か「必須の指摘 n 件」。

## 次に呼ぶスキル

- 必須の指摘あり → address（作った側）
- 新しい見た目の方向性の判断が要る → design
- 必須の指摘なし → merge-gate
