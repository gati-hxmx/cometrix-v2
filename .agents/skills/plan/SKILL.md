# 実装計画（plan）

## 手順

1. 仕様と関連コードを読み、変更するファイル・追加するテスト・手順を決める。
2. 次を Issue にコメントする。
   - 変更するファイルと、それぞれの変更内容
   - 画面がある場合：使う共通部品（[部品 5](../../../docs/design/components.md#5-共通部品を使い回す)）とパネルの形（[基本 6-1](../../../docs/design/layout.md#6-1-パネルにするかの判断)）、従うルールの章。新しい部品・色・アイコンが要るなら、ルールに足すことも手順に入れる
   - 追加・変更するテスト（受け入れ条件との対応）
   - 手順（小さく区切る）
   - リスク：壊れうる既存機能、性能、データ移行、セキュリティ
   - リスク判定の見直し（上がったらラベルを付け替える）
3. 影響が複数ファイルにまたがる、または方針が複数考えられるときは、別の AI に別案とリスクを聞く（Codex への依頼、または手元の `scripts/ai --review`）。意見を採用した／しなかった理由を書く。
4. 重要で方針が割れるタスクは、両方の AI に別ブランチで実装させて比べる方針を書いてもよい。

## 次に呼ぶスキル

- implement
- 計画の段階で高リスクとわかり、かつ方針自体に人の判断が要る → escalate
