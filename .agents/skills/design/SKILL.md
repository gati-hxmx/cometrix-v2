# デザイン案（design）

見た目の方向性はオーナーが選びます。AI は案を出し、選ばれた形をルールにして、以後は自走で同じ形を使います。既存のルールと部品の組み合わせで作れる画面には使いません（そのまま implement へ）。

## いつ使うか

- アプリを始めるとき（stack-select の後）：最初の画面と配色を決める
- 新しい種類の画面・部品で、ルールに形が書かれていないとき
- デザインの基本ルール（`docs/design/`）を変えるとき
- ui-review が「デザインの判断が要る」と書いたとき

## 手順

1. [デザインのルール](../../../docs/design/README.md) と関係する章を読み、使う人・どこで・何をしに開くか、375px の最初の画面に何を見せるかを決める。
2. 見本を作る。
   - **スマホ（375px）と PC（1440px）それぞれ4案ほど**。どの案も [見た目を選ぶときの考え方](../../../docs/design/README.md#見た目を選ぶときの考え方) と [配色](../../../docs/design/colors.md)・[アイコン](../../../docs/design/icons.md) を守る（絵文字は使わない、強い色の面は使わない）。
   - アプリの中に気に入られている画面があれば、その形から始める（考え方の1）。
   - 見本はアプリと同じ CSS 変数を使う HTML にし、Playwright でスクリーンショットを撮る。案ごとに「何がちがうか」を1行で書く。
   - 架空のデータを使い、空のとき・多いときの見え方も1枚入れる。
3. escalate でオーナーに選んでもらう。Issue（または PR）に案の画像を並べ、`needs-human` を付けて通知する。おすすめの案と理由を1つ書く。
4. 返事に合わせて詰める。「A と C を混ぜて」「赤が強い」のような返事なら、それを反映した次の2〜4案を出す。1回で決めきろうとしない。
5. 決まったら、同じ PR で次を直す。
   - 選ばれた形を `docs/design/` の該当する章に書く（新しい部品なら [部品 5](../../../docs/design/components.md#5-共通部品を使い回す) に足す）
   - オーナーの言葉をできるだけそのまま [経緯](../../../docs/design/history.md) に1行足す
   - 画面の仕様 `docs/screens/<画面>.md` に「使う人と最初の画面」と配置を書く
   - 配色を変えたら CSS 変数と [配色](../../../docs/design/colors.md) をそろえる

オーナーの返事を待つあいだは、デザインに関係しない作業（API・データ・テスト）を先に進める。

## 次に呼ぶスキル

- 案を出した → escalate（オーナーが選ぶ）
- 形が決まり、ルールに書いた → plan（作る画面がある）または ship（ルールの変更だけ）
